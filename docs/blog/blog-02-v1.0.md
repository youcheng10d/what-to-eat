# 今天吃啥 · 开发日志 02

v1.0 · 从 50 道模拟菜到 345 道真实菜品 · What to Eat

> 三小时就会过期的 token，三百多道真实的菜。

项目英文名 What to Eat（仓库 what-to-eat，下文简称 wte），中文名还在构思中，暂以「今天吃啥」相称。本文是 wte 开发日志系列的第二篇，记录从模拟数据走向真实数据的完整链路，以及这条路上一个始料未及的边界。

---

## 为什么要做真实数据

博客 01 结尾，我列了 v0.1 的三个诚实局限：50 道全是模拟、没有真实档口、纯前端。其中第二个最关键——一个帮你决定吃什么的工具，却回答不了「去哪个食堂、哪个窗口」，等于把最有价值的信息丢了。

所以 v1.0 只做一件事：把学校食堂真实存在的菜品搬进前端。

---

## 起点：三条路，选了抓包

把真实数据搬进来有三条路：

| 路线 | 可行性 | 问题 |
| --- | --- | --- |
| 找后勤 / 运营方合作 | 低 | 产品站消费者侧，会减少推荐难吃档口，不符合经营者的公平展示原则，合作从一开始就不可能 |
| 截图 + 多模态 LLM 结构化 | 可做 | 一次一张图，效率低；这是兜底方案，不是主力 |
| 小程序 API 抓包 | 最优 | 如果背后是通用平台，一次适配能覆盖多所高校 |

我选了第三条。本校订餐用的是「学府 e 生活」小程序，先跑通 PoC，验证这条路线到底行不行。

---

## 侦察：发现共性平台

用 PC 微信打开小程序，Reqable 抓包。结果比预想的好：

- 明文 JSON，没有请求签名，鉴权只有三个请求头（JWT + OpenID + Appid），脚本化可行性很高
- 域名是 api-order.lcsw.cn——不是城科自建系统，而是一家团餐 SaaS 服务商的接口，说明这大概率是一套共性平台
- 请求体里有 area_code 字段，城科的值是 10169588。换个 area_code 是不是就是另一所学校的菜单？这是让其他学校同学也用上 wte 的关键前提

侦察过程的完整记录固化在 docs/api-recon.md，包含所有端点结构、鉴权机制和分页逻辑。

---

## 打通采集管道

核心逻辑不复杂：

1. 调 /mini/shop/queryShopList 分页遍历所有档口
2. 对每个档口调 /api/merchant/getMchGoodsListV2，把完整菜单拉回来
3. 三个接口串成一个 PowerShell 脚本（tools/collect-lcsw.ps1）

踩的第一个坑：token 有效期只有 3 小时。JWT payload 里 exp - iat = 10800 秒，全自动无人值守采集不可行——每次采集前必须手动打开一次小程序换 token。所以脚本只能在本地跑，放不进 GitHub Actions。

踩的第二个坑：PowerShell 5.1 的 UTF-8 BOM 陷阱。脚本里有中文，改完之后 BOM 丢了，PS 5.1 按 GBK 解析直接 ParserError。修法是每次改完补一次 BOM。

打通后的第一次运行：4 个档口、1014 条原始菜品和商品数据。

---

## 清洗：从 1014 条到 345 道

原始数据是脏的：便利店一个档口就有几百条 SKU，大量是非食品；菜品没有分类标签，没有辣度，卡路里缺失。清洗脚本（tools/build-data.ps1）负责把它变成前端能吃的结构化数据：

- 分类：菜名关键词优先匹配（「米线」「盖饭」「糖水」），匹配不上的归入「其他」
- 便利店排除：先按分组名过滤非食品，后来干脆整个档口排除——便利店的食品不进推荐列表
- 辣度推断：菜名含「辣」默认中辣，「微辣」「麻辣」「爆辣」对应分级，无辣关键词默认 0
- 卡路里：按品类估算（面食 600、盖浇饭 700、家常小炒 450……），前端标注为估算值
- 甜品降权：糖水铺不当正餐推，用户没有甜品意图时，甜品饮品 -8 分

清洗后 405 道进入推荐池；第二天把便利店整档口排除，剩 320 道；补采时新增古茗商业街，最终 345 道。

---

## 前端接入：静态 JSON 优先读真实数据

v0.1 的前端已经留好了后门：api.js 里数据源优先级是 window.DB_REAL（真实数据） || window.DB（模拟数据兜底）。真实数据以 data.js 的形式放进 data/ 子目录，结构和模拟数据完全一致，并加了缓存破坏参数强制刷新。

推荐引擎一行没改——它只认数据结构，不认数据来源。

---

## 全链路通了，但只有五个档口

采集管道、清洗管道、前端接入，全链路打通。我以为 v1.0 就这么成了——直到发现一个事实：

小程序上只有 5 个档口。

公社食堂小炒、古春堂凉茶糖水铺、惠盈便利店、古茗商业街、外公家米线。就这五个。

但我每天下楼吃饭，食堂明明有十几家档口：兴旺法式铁板烧、你过来啊烤鸭饭、椰子鸡黄焖鸡、沈大爷拌饭拌面……这些都不在小程序里。

后来搞明白了：学府 e 生活是一套外卖 SaaS，线下堂食档口很多没入驻。抓包能读到的，只有入驻过的档口；没入驻的，一条都抓不到。

也就是说，脚本这条路能覆盖 LCSW 平台上的所有学校，却覆盖不了一所学校的所有档口。而我要做的是「让同学找到自己爱吃的」，不是「只推荐能点外卖的」。

---

## 转向线下拍照

所以我改了主力方案：线下逐档口拍照、手动录入菜名和价格。今晚就下楼，先把城科的所有档口拍全、录入干净，让 wte 真正能推荐同学每天在食堂吃得到的东西。

这里必须说清楚：脚本没有废掉。恰恰相反，它依然重要——LCSW 平台覆盖了多所高校，后续我会把脚本升级成能完整读取学府 e 生活全部档口和菜单的通用版本，让使用同一套小程序的其他学校同学也能用上 wte。只是现在，为了让城科的版本尽快真正可用，先拍照、再录入。

这是一个取舍：功能可实现性优先于功能多样性。

---

## 安全与合规

脚本里的 token 和 openid 属于个人凭证，提交前全部清空，数据文件也检查过不含个人信息。采集只取事实信息（菜名、价格、档口名、营业时间），不碰用户评论文本；请求间隔 1.2 秒以上，对服务保持克制。

---

## v1.0 的诚实局限

- 小程序只有 5 个入驻档口，覆盖不了全校，线下照片录入是目前的主力方案
- token 3 小时过期，每次采集前要手动抓一次新 token
- 卡路里是品类估算值，不是真实营养数据
- 分组过滤靠关键词启发式，长尾误判需要持续修

---

## 写在最后：执行力的续篇

博客 01 把爱迪生的「99% 的汗水加上 1% 的灵感」读成了这个系列的注脚：1% 的灵感，加上 99% 的执行力。

v1.0 是一次小小的试错。我以为跑通 API 就能拿到完整数据，实际上 SaaS 平台的边界限制了它。但采集、清洗、接入这条链路是真实可用的，只是数据的源头需要换一个。

1% 的灵感，是侦察时意识到「学府 e 生活不是学校自建，而是 SaaS」的那个瞬间：它意味着数据结构标准化、一次适配可能覆盖多所高校。这个判断没有写在任何文档里，是盯着 API 域名一条条拼出来的。

99% 的执行力，是补 BOM、修分页、三组请求体逐个试错，是盯着 1014 条原始数据逐类核对清洗规则，也是发现边界之后迅速改主意的决断。AI 加速了其中大半，但「下一步该试什么」的判断，仍然要人来下。

今晚要做的事很朴素：拿着手机下楼，一个档口一个档口地拍菜单、录菜名、记价格。这一环 AI 帮不了，是实打实的体力活。灵感指出方向，执行力负责把数据一个个搬进来。
