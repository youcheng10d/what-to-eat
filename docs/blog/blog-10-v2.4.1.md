# 吃嘛 · 开发日志 10 ⭐ 一块九的麻辣烫，和会漂的 id
> ***v2.4.1*** ｜ 只动构建脚本与 data.js：2582 → 2382 道，两次重建 id 漂移 0。工具：PowerShell 5.1、Node 24。

推荐池里有一份 1.98 元的麻辣烫。

不是特价，也不是小份。牌面上写的是“1.98 元/50 克”，识别的时候把每 50 克的单价当成了整份售价。本文记这两处数据修正——称重计价与 id 漂移，以及一个被 CI 引用了、却从来没提交过的测试脚本。

---
## 先给结论
• 称重档口的牌面单价被当成了整份售价：麻辣烫 1.98 元/50g 显示成 ¥1.98，预算 5 元的过滤会把它当成一块九的菜。  
• 现在 `price` 存按 400g 估的每份价（¥15.8），`unitPrice` 存牌面单价（1.98 元/50g），卡片上两者并列，并注明“元·估”。  
• 198 组菜被两个来源各录了一次，去重结果取决于哈希表的枚举顺序；同一份输入两次构建，195 条菜的描述与 id 来回抖。  
• id 从顺序发号改为 `hash(档口|菜名)`，价格不参与；两次重建 0 漂移，2382 条 id 全部唯一。  
• 七个回归脚本与数据校验全过；金文件里的 `budget-meat` 九条结果人工核过，全部 ≤15 元。

## 一块九的麻辣烫
问题是在整理数据时看到的：一道菜叫“麻辣烫/麻辣拌”，档口是章尚村麻辣烫，价格 ¥1.98。

翻回采集记录，牌面写的是“1.98 元/50 克”。OCR 只取了数字，把单位丢了。同样的还有一家轻食档口，“1.78 元/50 克”被记成 ¥1.78。

影响不止是卡片上少写了一个零。

预算过滤读的是 `price`。用户写“预算 5 元”，麻辣烫以 1.98 元通过筛选，再以“便宜、管饱”的理由被推到第一张卡。用户看到的是一块九，结账时称出十五块八，中间差了八倍。

修法不复杂：构建期认出“元/50 克”这个模式，把两个价格分开存。

| 字段 | 例子 | 用途 |
| --- | --- | --- |
| `price` | 15.8 | 预算过滤、卡片主价 |
| `unitPrice` | 1.98 | 牌面单价，只用于展示 |
| `unit` | 50g | 计价单位 |
| `estPrice` | 15.8 | 按 400g 估的每份价 |
| `pricing` | weight | 标记为称重菜 |
| `tags` | 称重 | 卡片角标与后续筛选 |

识别规则写在 `tools/build-data.ps1` 第 6.95 步，正则只认这一种写法：

```powershell
if ($text -notmatch '(\d+(?:\.\d+)?)\s*元?\s*/\s*50\s*克') { continue }
$unit = [double]$Matches[1]
$est  = [math]::Round($unit * 8, 1)
```

乘 8 是因为 400g 里有八个 50g。1.98 × 8 = 15.84，保留一位小数后是 15.8；1.78 × 8 = 14.24，记 14.2。

卡片上的展示改成两行：

```
¥15.8 元·估
牌面 1.98 元/50g，按 400g 估一份；实际以称重结算
```

“元·估”三个字是故意的。称重菜没有标准份量，任何整份价都是估的，不能写成确定值。
> 单价不是售价。把这两个数混在一个字段里，预算过滤会跟着一起错。

## 四百克是估的
为什么是 400 克，不是 300 克或 500 克？

没有称重记录，也没有消费小票。400 克是“一碗麻辣烫”的常见取量，属于产品假设，不是测量结果。它只影响两件事：卡片上那个参考价，以及预算过滤时按多少算。

写进代码时留了三个出口：`estPrice` 单独存、`unitPrice` 单独存、卡片上同时显示“实际以称重结算”。这样即使 400 克估偏了，用户看到的牌面单价仍然是真的，预算过滤也只会错在“估”的那一部分。

局限也写清楚：目前只认 `元/50克`。`元/100克`、`元/斤`、按串计价都还没覆盖，遇到时仍会按普通菜处理。
> 估算可以出现在卡片上，但必须带着“估”字出现。

## 会漂的 id
第二处问题更隐蔽：id 会随着数据重建而漂移。

起因是 198 组菜被两个来源各录了一次——一部分来自小程序接口，带图；一部分来自线下逐档口拍照，描述更细。合并时用的是哈希表，同名的后来者覆盖先来者，谁被留下取决于枚举顺序。

结果是同一份输入，两次构建出来的描述与 id 不一样。实测有 195 条菜在两个版本之间来回抖。

第二个原因更直接：id 从 10000 开始顺序发号。只要在中间插入或删除一道菜，后面所有菜的 id 全部平移。用户存在 `localStorage` 里的收藏、今天吃过、吃过次数，全都指到别的菜上。

| 存储键 | 存的是什么 | 漂移后的后果 |
| --- | --- | --- |
| `wte.favorites` | 收藏的菜 id | 收藏变成另一道菜 |
| `wte.eatenToday` | 今天吃过的 id | “今天吃过”记错 |
| `wte.dishCount` | 每道菜吃过几次 | 次数串到别的菜 |

修法分两步。

第一步，收敛重复时用固定优先级，不再依赖枚举顺序：带图的优先于不带图，接口来源优先于线下录入，描述更长的优先于更短的，标签取并集。

第二步，id 改成内容哈希：

```powershell
$key   = "$($d.stall)|$($d.name)"
$md5   = [System.Security.Cryptography.MD5]::Create()
$hash  = $md5.ComputeHash([System.Text.Encoding]::UTF8.GetBytes($key))
$newId = [int]([BitConverter]::ToUInt32($hash, 0) % 900000000) + 100000000
```

价格不参与哈希。调价不会让用户的收藏失效；改菜名会生成新 id，这是可接受的——菜名变了，本来就该当成另一道菜。

收敛后：2582 道变 2382 道，2382 条 id 唯一，连续两次构建 id 变化 0。
> id 不是内部实现，它是用户数据的主键。

## 验收
数据改完，先跑重建，再跑回归。

| 检查 | 结果 |
| --- | --- |
| 连续两次构建，id 变化数 | 0 |
| 唯一 id 数 | 2382 |
| 同名同档口重复 | 0 |
| 称重换算命中 | 2 道 |
| 数据校验 | 2382 道 / 65 档口 |
| 七个回归脚本 | 全过 |

金文件测试有一项 `budget-meat`（预算 15 元、要吃肉），六个用例各跑三轮，一共九条结果。数据重基之后逐条人工核对，九条全部 ≤15 元，才执行 `--update`。

金文件不是“跑挂了就更新”。它是推荐行为的快照，只有确认新结果符合预期，才有资格改。
> 数据改了，金文件必须跟着改；但只能人工确认之后改。

## CI 里的幽灵脚本
收拾数据时顺手看了一眼 CI，发现流水线里引用了两个文件：`tools/sync-standard.mjs` 和 `tests/edition.test.mjs`。仓库里一个都没有。

前一个是当时想把 Pro 的通用代码同步回无 AI 版本，写了个脚本，只在本地跑过，没提交；后一个是版本隔离校验，写了标题，内容还没落盘。CI 一旦跑起来，第一步就会红。

处理方式是把测试写成自包含的：不依赖同步脚本，自己读文件、自己断言。`tests/edition.test.mjs` 现在有十项检查，覆盖目录存在、禁止文件、页面引用、摄像头调用与数据一致性。

这件事的教训比脚本本身重要：**测试必须能在一个干净的 checkout 里跑起来。** 依赖一个只在本地存在的文件，等于没有测试。

## 没做完的
• 只认 `元/50克`；`元/100克`、`元/斤`、按串计价还没覆盖。  
• 400 克是产品假设，不是称重记录；取量偏大或偏小时，参考价会跟着偏。  
• 自选麻辣烫那条虚拟菜仍是档口真菜的中位价，不是称重价，两套价格逻辑并存。  
• id 哈希冲突用 `+1` 兜底，2382 条里没撞过，但没做过万级压测。

## 写在最后
*“1% 的灵感，加上 99% 的执行力。”*

这一篇的 1%，是把 id 当成用户数据的主键，而不是数组下标。想通这一点之前，重建数据只是“重新生成一份文件”；想通之后，每一次重建都要对用户手机里的收藏负责。

99% 的执行力，是认出那一行“1.98 元/50 克”、给 198 组重复菜定一条与顺序无关的优先级、把顺序发号换成内容哈希、连续重建两次比对 id，也是承认 CI 里引用了一个不存在的脚本，然后把它补成能独立跑的自包含测试。
