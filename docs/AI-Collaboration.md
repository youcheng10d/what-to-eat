# AI 协作与开发演进记录

> 本文件用于满足赛题“开发全链路可复现”的要求：记录作品的诞生过程、关键 Prompt 与设计决策，便于他人理解与确定性复现。

---

## 1. 原始需求（Prompt）

> 作为一个前端工程师，请帮我创建一个“今天吃啥”的移动端风格 Web 应用。要求：
> 1. 页面简洁美观，有食欲感。
> 2. 顶部有一个输入框，用户可以输入自己的饮食偏好（如：减肥、预算 15 元、不想吃辣）。
> 3. 下方有一个显眼的“替我决定！”按钮。
> 4. 点击按钮后，从模拟的 50 道大学食堂菜品数据中，智能筛选并推荐一个菜品，并以卡片形式展示菜品名、价格、卡路里和推荐理由。

---

## 2. 关键设计决策

### 2.1 技术栈选择
选择 **纯静态 HTML + CSS + 原生 JavaScript**，而非 React/Vite 等构建型方案。

理由：
- 核心交互为单页轻量交互，无需组件级状态管理或构建工具；
- 交付形态要求“可离线直接打开”，纯静态零依赖最稳；
- 便于评审者零门槛复现与查看。

### 2.2 分层架构
刻意做了“数据 / 服务 / 视图”三层分离，避免逻辑全部堆在一个文件里：

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 数据层 | `mock.js` | 唯一数据源，50 道菜品集中存放 |
| 服务层 | `api.js` | 偏好解析、过滤、打分、生成理由；暴露异步接口 |
| 视图层 | `app.js` | 状态管理、DOM 渲染、交互绑定 |

这样后续替换真实后端时，只需改 `api.js` 内部实现，视图层不动。

### 2.3 接口先行
`api.js` 中的 `recommendDish(preferences, { excludeIds })` 虽然内部是本地实现，但**按真实 API 的方式定义签名、模拟网络延迟、返回统一结构**，并标注接入点：

```js
// TODO: replace with fetch('/api/recommend')
// 请求: { preferences: string, excludeIds?: number[] }
// 返回: { code: 0, data: { dish, matched, reason, relaxed, relaxedNote } }
```

### 2.4 推荐策略：硬约束 + 软偏好 + 兜底
纯随机没有“智能感”，纯严格过滤又常常无解。最终采用三段式：

1. **硬性过滤**：预算、卡路里、忌辣、素食四类条件直接筛除。
2. **逐级放宽**：若过滤后为空，按 `卡路里 → 预算 → 素食 → 忌辣` 顺序逐项放宽，并记录放宽项，在结果卡片上如实告知用户。
3. **软性打分**：对品类、口味、标签等软偏好加权计分，叠加随机抖动后取 top5 再做加权随机，兼顾“贴合偏好”与“每次不一样”。

### 2.5 视觉方向
定位为“暖调食堂编辑风”：奶油纸感底色 + 柿子橙主色 + 番茄红点缀，楷体大字标题，柔和层叠阴影与细点纹理背景，强化食欲感；移动端 430px 单列布局。

## 4. 验证方式

1. **静态代码审查**：检查资源引用完整性、`id` 唯一性、事件绑定、图标引用一致性、状态覆盖（loading / empty / error / disabled）、无外部依赖。
2. **语法编译检查**：对 `mock.js` / `api.js` / `app.js` 执行语法校验，全部通过。
3. **手动验收**：覆盖典型场景——含条件的推荐、条件无解的放宽提示、“换一个”排除逻辑、刷新后草稿保留、移动端窄屏布局。

## 6. 复现方式

1. 克隆仓库，双击 `what-to-eat/index.html` 即可运行（无需任何依赖）。
2. 按第 2 节的设计决策逐层对照源码，即可还原完整实现路径。
3. 若需接入真实后端，参照 `api.js` 中的 `TODO` 接入点替换实现，保持入参与返回结构不变。
